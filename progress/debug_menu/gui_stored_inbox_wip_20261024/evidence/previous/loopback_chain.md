## Why 337 and 143 are not one-off fixes

- Event 337's existing `HudMessageAnalyzer::Update` consumer reads the GUI input event queue. Event 143's existing `DispatchInboundGuiEvents` arm updates `SystemUserProfile` and refreshes sign-in state. A channel-40 producer wrapper can recover the exact output record, but it does not by itself provide that record to either module-input consumer on PC.
- The faithful dependency is the generic module-level output-to-next-input owner and dispatch order, together with the PC observer-fanout replacement and the current overlay-specific late-reader seat. A one-event append at either sink would invent a special route; appending the whole queue without reconciling current `RouteEventToFlow` creates duplicate delivery.
