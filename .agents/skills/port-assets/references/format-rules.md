# Format rules for porters

## The `bnd2` container

- Header: magic `bnd2`, then u32 fields at +4 version, **+8 platform** (2 = Xbox 360
  big-endian, unconverted; 4 = the little-endian form the PC loader requires), +12 debug-data
  offset, +16 resource count, +20 entries offset, +24/+28/+32 the three data-block offsets, +36
  flags (bit 0 = compressed). Resource entries are 64 bytes each and start with the u64 resource
  id. `tools/diagnostics/dump_bundle.py <file>` prints them for a platform-4 bundle; the stager's
  own platform sniff reads +8 in both byte orders.
- Assert the container invariant `entriesOffset + count * 0x40 == dataOffset[0]` in every porter:
  a corrupted resource count is otherwise invisible, because YAP reads the same wrong count and
  the port "succeeds" on a short bundle (`tools/assets/bundles/engine_transcode.py` does this).

## Names are stored as hashes

- A `bnd2` stores no names, only resource ids: the CRC32 of the lowercased name
  (`resource_id()` in `tools/assets/bundles/particles_transcode.py`). A text search of bundle
  data for an asset name can only fail: a leg once reported an image "not in the converted data"
  that was resource 4 of `GUITEXTURES.BIN`, already ported. Hash the name and search for the id.
  Retail payloads can also be zlib-compressed, a second reason a byte search fails.
- AttribSys keys are 64-bit Bob Jenkins lookup8 hashes with seed `0xABCDEF0011223344`: a class
  key is `hash64("<class name>")` and a collection key is `hash64("<decimal id>")`. Python:
  `hash64()` in `tools/assets/bundles/vehicleattrib_transcode.py`; C++, with the identities it
  attests: `b5-decomp/src/SDKs/Packages/AttribSys/1.2.1.2/AttribSys/runtime/common/attribhash64.cpp`.
  Every vault key is a name lookup, never a mystery, and a class with no generated `KI_*_CLASS`
  in the tree still has a name (`physicsvehiclehandling` is the hub every car asset points at).

## How wide is a serialised slot? Decide per struct, then per slot

- A pointer-shaped slot in a serialised record is as wide as the committed PC consumer reads it,
  never what the DWARF's pointer type says.
  - Where the consumer's FixUp rebases a 32-bit word in place (resources live below 4 GB), the
    slot stays 4 bytes and the stride does not grow; declaring a host pointer there reads garbage
    (`BrnVehicle::GraphicsSpec`, `StreamedDeformationSpec`: `u32` slots behind a widening accessor).
  - Where the consumer declares a real host pointer member, the porter re-lays the record out for
    x64, and the manifest rule says so (`prop-physics`, `world-support`, the environment
    timeline rules), with the C++ side pinned by `static_assert` / `_AssertLayout()`.
- A struct carved at runtime, never deserialised, widens its pointers like any host object; a
  struct with no pointers keeps the console offsets.
- Widening can break alignment that no compile or link catches: a member that sat 16-aligned on
  the console moved to `+0x24`, and the first `movaps` on it faulted. After widening anything in a
  struct that holds SIMD data, check the alignment of what follows it.

## Byte order: the shipped file decides

Our transcoders normalise endianness, so a faithful transcription of a console reader can be
wrong against a ported asset: `CgsPolygonSoup`'s packed vertices are little-endian in our
bundles (`world_support_transcode.py` reads them as `'<3h'`), while the console reader assembles
them big-endian. When you reconstruct or check a reader of serialised data, verify its byte order
against the shipped file. A wrong-endian read of packed shorts yields plausible small numbers:
it looks like "there is no data here", not like an error.

## Swap a field by its real composition

- `attribsys_transcode.py` once swapped the tail of `Attrib::CollectionLoadData::Entry` as one
  u64, because a PtrN record names that slot, when it is `{u32, u16, u8, u8}`. `mu8Flags` moved
  from `+0x0E` to `+0x09` in every ported vault and every array attribute lost its `0x2` flag: the
  intro camera group played 1 shot instead of 3, and the world's surface list resolved 1 surface
  instead of 20. The entry never widened; it is 16 bytes on both targets.
- Blanket u32 swaps fall into the same trap: `Attrib::Array`'s head is four u16s, and
  `EA::Reflection::Bool` is one byte.
- AttribSys vaults also keep a current base that type-2 records select; see the manifest's
  `postfx-vault` rule before touching the fixup walk.
- When a shared porter is found defective, re-verify every bundle it ever emitted: the reported
  symptom is rarely the only one.

## Layout oracles already in the data

- `schema.vlt` / `schema.bin`, generated by `build devdata` from the XEX's `.rdata`, carry the
  AttribSys class definitions (key, type, offset, size, count, alignment) for every class: an
  independent layout oracle, not circular with our headers. `build/` is ignored, so regenerate it
  rather than assume it is present.
- burnout.wiki pages are authority for field names and types, never for offsets (AGENTS.md).
